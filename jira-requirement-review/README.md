# Jira Requirement Review Agent

Two Aetherion agents that review Jira requirements and help a human post a
clarification comment. See [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) for
the full design.

## What it does

1. **`JiraRequirementReview`**
   Reviews **one issue** (`issue_key`) or a **batch** of issues matched by a
   Sprint/JQL query (`jql_override`) — merged in from the pre-grooming clarity
   agent this feature set combines. For each issue it reads the target's
   **description + comments**, its **parent card's description + comments**,
   **all subtasks' descriptions + comments**, its **linked issues**
   (blocks/relates-to/etc.), and an optional **meeting transcript** (file upload,
   which may cover multiple cards). An LLM produces findings across nine
   categories — **Assumptions, Open Questions, Requirement Gaps, Ambiguities,
   Edge Cases, Missing Functional Details, Missing Technical Details, Missing
   Acceptance Criteria, Dependency Questions** — each with an *evidence source*
   and a *confidence* level (Ambiguity/Dependency Question also carry a
   *priority*), plus an overall **readiness score (1-5) and executive summary**
   per issue.

   Delivery is a set of independent, opt-in toggles:
   - **`Publish to Jira`** (default OFF) — posts the review as a comment
     directly on each reviewed issue; OFF just returns an editable draft (in the
     `Message` field) for you to copy into Jira's comment box yourself.
   - **`Generate Word Report`** (default OFF) — also produces a consolidated
     `.docx` report across everything reviewed, as a download link. Requires
     object storage (`TENANT_ID`) configured.
   - **Send Email — TEMPORARILY DISABLED.** The underlying delivery (via the
     Pulsar notification service, same mechanism as `my_first_agent`'s
     `send_jira_summary_email`) is implemented and unit-tested
     (`src/tools/send_review_report_email_tool.py`), but it has no trigger in
     `metadata.json` and `agent/review_flow.py` force-sets `send_email = False`
     regardless of payload, so it cannot currently be invoked — even directly via
     API. Re-enable by restoring the trigger and the `payload.get("send_email", ...)`
     read once Pulsar recipients/template are confirmed for this agent.

2. **`PostJiraReviewComment`** (post a specific, human-edited comment)
   Posts a comment you supply (`comment_markdown` or `findings`) to the issue,
   with a "Generated by …" timestamp footer — use this to publish a draft you
   edited yourself.

Default is **draft-only, single-issue, no report** (a human-in-the-loop gate);
flip the relevant toggle on for batch review, direct posting, or a Word report.

## Configuration

Copy `.env.template` → `.env` and set:

```
JIRA_BASE_URL=https://your-site.atlassian.net
JIRA_EMAIL=you@example.com
JIRA_API_TOKEN=...                  # Atlassian API token (HTTP Basic auth)
LLM_MODEL_ID=gpt-5.1                # must be a model the gateway has a key for
# LLM_PROVIDER=openai               # OPTIONAL: override provider detection
# TENANT_ID=your_team_bucket        # OPTIONAL; needed for transcript reads and generate_docx uploads.

# === Email distribution (Pulsar notification service) — send_email is
# TEMPORARILY DISABLED (no trigger, force-off in review_flow.py); these are only
# needed once it's re-enabled.
# NOTIFICATIONS_BASE_URL=http://localhost:8010
# JIRA_NOTIFY_EMAILS=you@example.com,teammate@example.com   # resolved to UUIDs via public."user"
# JIRA_NOTIFY_USER_IDS=uuid-1,uuid-2                        # alternative: skip the DB lookup
```
`LLM_MODEL_ID` must be a model the **AI Gateway has a provider key for** — the
provider is derived from the id prefix. OpenAI ids (`gpt-5.1`, `gpt-5`, `gpt-5-mini`)
work; Claude ids (`claude-*`) require an Anthropic key configured in the gateway.
`OPENAI_MODEL_ID` is still honoured for backward compatibility.

LLM calls go through the **Aetherion AI Gateway** (`agent_lib.gateway.ai`), which
holds the provider credentials centrally — so **no `OPENAI_API_KEY` is needed** in
the agent or its pod.

Once `send_email` is re-enabled, it will require `NOTIFICATIONS_BASE_URL` plus
either `JIRA_NOTIFY_EMAILS` (resolved to `public."user".id` UUIDs via a DB
lookup — needs platform DB connectivity) or `JIRA_NOTIFY_USER_IDS` (UUIDs
directly, skips the DB). The `jira_requirement_review_report` template must also
be registered on the platform's Pulsar instance; if it isn't, the notification
call returns a non-200 and `email_status` surfaces `"error"` rather than the run
failing.

## Run locally

```bash
uv sync
# two terminals (source the venv in each):
aetherion run --tool
aetherion run --agent
```

### 1) Generate a draft (default — nothing posted)

```bash
aetherion agent JiraRequirementReview \
  '{"issue_key":"ABC-123","include_parent":true,"include_subtasks":true,"post_to_jira":false}'
```

The result's **`Message`** field contains the ready-to-paste draft (plus
`comment_markdown`, `findings`, `comment_adf`). Copy it into the Jira comment box
yourself and publish. **Nothing is posted to Jira by this step.**

Optional transcript (requires `TENANT_ID` bucket + an uploaded file):
```bash
aetherion agent JiraRequirementReview \
  '{"issue_key":"ABC-123","uploaded_files":"meeting.txt"}'
```

### 1b) …or let the agent publish directly

Turn the **`Publish to Jira`** toggle ON (`post_to_jira: true`) and the agent posts
the review as a comment on the issue itself:
```bash
aetherion agent JiraRequirementReview \
  '{"issue_key":"ABC-123","post_to_jira":true}'
```
If the post fails, it falls back to returning the draft so you can paste it manually.

### 1c) Batch review a Sprint/JQL query

```bash
aetherion agent JiraRequirementReview \
  '{"jql_override":"sprint = \"Sprint 42\" AND status = \"To Do\""}'
```
Each matched issue (capped at `MAX_JQL_RESULTS`, default 25) runs the full
per-issue pipeline above. Combine with `post_to_jira` and/or `generate_docx` as
needed.

### 1d) Word report

```bash
aetherion agent JiraRequirementReview \
  '{"jql_override":"sprint = \"Sprint 42\"","generate_docx":true}'
```
Returns an `s3_download_link` entry for the `.docx` report (requires `TENANT_ID`).
`send_email` is temporarily disabled (see above) — the report is download-only
for now.

### 2) Post a comment you edited yourself

To publish a draft you tweaked, use the dedicated post agent:

```bash
aetherion agent PostJiraReviewComment \
  '{"issue_key":"ABC-123","comment_markdown":"<the approved/edited markdown>"}'
```

> ⚠️ **UI note (`metadata.json`):** the Aetherion package `metadata.json` declares
> one agent + one trigger form, which here describes **`JiraRequirementReview`**.
> `PostJiraReviewComment` is registered and fully runnable **by name** (CLI/JSON as
> above; payload = `issue_key` + `comment_markdown`, or `issue_key` + `findings`),
> but it does not get its own auto-generated UI form from this single metadata file.
> Confirm with the platform how a multi-agent package should expose a second
> trigger form before relying on a UI launch for the post step.

## Layout

```
src/
  config.py            # env settings, size caps, team_id resolution
  agent/               # deterministic orchestrators (review_flow/post_flow) + SDK bindings
  tools/               # @tool activities; analyze_requirement calls the Aetherion AI Gateway;
                        # send_review_report_email_tool calls the Pulsar notification service
  jira/                # HTTP helpers + JiraClient (issue fetch, parent, subtasks, linked issues, comments, JQL search, comment POST)
  context/             # ContextSource abstraction + sources (incl. linked issues) + registry + payload budget
  review/              # Finding/Review/Readiness models, parser, dedup, prompt, ADF rendering, LLM-response parsing, report (DOCX/email) rendering
  utils/                # db_handler: email -> public."user".id UUID resolution for Pulsar
  shared/              # MIRROR of ../shared — do not edit here (see below)
```

### The shared package

`src/shared/` is a **mirror** of the canonical `../shared/`, carried inside this
project because the Aetherion packer builds each tarball from that project's own
`src/` directory. Editing the mirror fails `tests/test_shared_in_sync.py`.

```bash
python ../scripts/sync_shared.py     # after changing ../shared/
```

It provides attachment extraction (PDF, Word, Excel, PowerPoint, CSV, JSON,
images), Confluence page reading, ADF in both directions, the environment
readers and the result contract. Shared code does its HTTP through the narrow
`Transport` port, and this agent's `aiohttp` adapter is `src/jira/transport.py`
— which is how the same Confluence reader serves an agent built on `httpx`.
See [../shared/README.md](../shared/README.md).

Adding a new context source (Confluence, Slack, …) is a single new
`ContextSource` subclass registered in `src/context/registry.py` — no orchestrator
or prompt changes.
